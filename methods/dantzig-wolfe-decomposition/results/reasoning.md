I'm looking at a block-angular LP: `min sum_k c_k^T x_k`, subject to `sum_k A_k x_k = b` and `x_k in X_k`, where `X_k = {x: B_k x <= d_k, x >= 0}` is each block's own local feasible region, and only the handful of rows `sum_k A_k x_k = b` couple the blocks together. Handing all the `x_k` to a single simplex solver certainly works, but the solver then has to carry both each block's internal constraints `B_k x_k <= d_k` and the global coupling at once — the structure isn't being exploited. What I want to ask is whether "global coordination" and "within-block feasibility" can be separated algorithmically.

Let me first think of the crudest block-wise method: each block independently solves `min c_k^T x_k` s.t. `x_k in X_k` using its own `c_k`, and then some patching step tries to fix up the coupling constraint. This is cheap, but it's wrong right away: the independent per-block optima will almost certainly not satisfy `sum_k A_k x_k = b`, and the patching step has no principle to it — it doesn't know which block should give something up, or how much. The problem is that each block is using its own `c_k` and has no visibility at all into the scarcity implied by the coupling constraint. So splitting into blocks isn't itself the hard part; the hard part is getting each block to "sense" the global price while it's being solved. This suggests that the dual price `pi` of the coupling constraint ought to be fed back into each block's objective.

So should I change the "unit" the variables are expressed in? In the original LP, the variables are the coordinates of `x_k`, and the master directly decides how much of each coordinate to take, which is why the local constraint `B_k x_k <= d_k` has to stay in the master. Could I instead package up local feasibility as a whole, so the master no longer sees local coordinates at all? There's a representation fact about convex polyhedra: if `X_k` is a nonempty bounded polyhedron, every point in it is a convex combination of its extreme points, `x_k = sum_r lambda_kr p_kr`, `sum_r lambda_kr = 1`, `lambda_kr >= 0`. Substituting this back into the original LP makes the original coordinates `x_k` disappear, and the master's variables become the weights `lambda_kr`. The objective becomes `sum_k sum_r (c_k^T p_kr) lambda_kr`, the coupling constraint becomes `sum_k sum_r (A_k p_kr) lambda_kr = b`, and we add one convexity row `sum_r lambda_kr = 1` per block. A column no longer corresponds to "increase some coordinate by 1" but to "adopt a bit of the weight of subproblem k's r-th complete extreme-point plan." The crucial point is that local feasibility is automatically baked in: as long as a column comes from an extreme point of `X_k`, any convex combination of such columns is still in `X_k`, so `B_k x_k <= d_k` can never be violated. The master no longer has any local constraints at all — only the coupling constraint plus the convexity constraints.

On the surface this reformulation looks worse, because the number of extreme points of `X_k` can grow exponentially with dimension, so there would be exponentially many columns. But I don't need to list them all. The logic of simplex is: after solving a restricted master, to decide whether there's still room to improve, all that's needed is to check whether any column not yet listed has negative reduced cost — there's no need to know the whole set of columns. For block `k`, the master gives me the dual `pi` of the coupling constraint and the dual `mu_k` of that block's convexity constraint. A column for extreme point `p` has objective coefficient `c_k^T p`, coefficient `A_k p` in the coupling row, and coefficient 1 in its own convexity row, so its reduced cost is `c_k^T p - pi^T (A_k p) - mu_k = (c_k - A_k^T pi)^T p - mu_k`. Finding the most negative reduced cost over all extreme points is, since `mu_k` doesn't depend on `p`, equivalent to solving `min_{p extreme} (c_k - A_k^T pi)^T p`. Because the optimum of a linear objective over a polyhedron is attained at an extreme point, this minimization can be carried out directly over the whole `X_k`: `min_{x in X_k} (c_k - A_k^T pi)^T x`. This is itself a small LP, and simplex will return an extreme point — exactly the column I need. This also answers the puzzle from before, about how a block is supposed to "sense" the global price: it subtracts `A_k^T pi` from its own objective, and that is precisely the shadow price of the coupling constraint.

So the shape of the algorithm is now clear: start with a few feasible columns per block, solve the restricted master, read off `pi, mu_k`, solve the pricing subproblem for each block; if some block's optimal reduced cost is negative, add that column to the master, and stop once every block is nonnegative. The master is responsible for global resources and convex combination, the subproblems are responsible for local feasibility and the optimal response to prices; the information flow is that the master passes down prices and the subproblems pass back columns.

I'm worried about two things I'd be claiming true without checking: first, the stopping condition "nonnegative for all blocks means globally optimal"; second, whether the solution I get after swapping local coordinates for extreme-point weights is still a solution of the original LP. Let me run the whole chain on a minimal instance. Take two scalar blocks, each `X_k = [0,1]`, objective `min 2 x1 + x2`, coupling constraint `x1 + x2 = 1`. Each block has just two extreme points: `{0, 1}`. Solving the compact LP directly, the optimum is `x1=0, x2=1`, objective 1, and the dual of the coupling constraint is `pi = 1` — this is the reference answer I'll check against.

Now let's run it Dantzig-Wolfe style. I'll deliberately give an asymmetric initial column pool, to see whether it can self-correct: block 0 gets two columns (`x=0` and `x=1`), block 1 gets only one (`x=0`). In the first restricted master, block 1's contribution to the coupling constraint is pinned at 0, so the coupling row `x1 + x2 = 1` has to be entirely carried by block 0, forcing block 0's `x=1` column to weight 1. Solving this gives master objective = 2, dual `pi = 2`, `mu = (0, 0)`. Now pricing: for block 0, `coeff = c_0 - A_0 pi = 2 - 1*2 = 0`, the optimal extreme point is `x=0`, reduced cost `0*0 - 0 = 0`, no improvement; for block 1, `coeff = 1 - 1*2 = -1`, the optimal extreme point is `x=1`, reduced cost `(-1)*1 - 0 = -1 < 0`, so block 1's `x=1` column `(cost=1, link=1)` gets added.

With block 1's `x=1` column now available, the second master can let block 1 carry the coupling demand: it solves to `x1=0, x2=1`, master objective = 1, dual `pi = 2`, `mu = (0, -1)`. Pricing again: block 0 has `coeff = 0`, takes `x=0`, reduced cost 0; block 1 has `coeff = -1`, takes `x=1`, reduced cost `(-1)*1 - (-1) = 0`, exactly zero, no longer negative. Neither block has a negative reduced cost, so we stop. Final objective 1.0000, converged in one iteration.

This number matches exactly the 1.0 and the optimal point `x1=0, x2=1` obtained by solving the compact LP directly, so "switching to extreme-point weights" really has not changed the LP's optimal value; and the asymmetric initial column pool was automatically fixed up by the pricing step. Something I should honestly note: the `pi` I'm comparing against isn't quite the same — the compact LP gives `pi=1`, while the DW master gives `pi=2` at convergence. This isn't a contradiction: the coupling constraint is an equality, `x=[0,1]` is at an active boundary, so the dual isn't unique, and both `pi` values are legitimate optimality certificates as long as all reduced costs are nonnegative — and indeed the two blocks' reduced costs computed above are both `>= 0` under `pi=2, mu=(0,-1)`. This is exactly what verifies the stopping condition in the way I wanted: nonnegative reduced cost across all implicit columns (here, just the extreme points that were never explicitly added) constitutes a dual certificate for the full master, and hence for the original LP; it isn't the empirical claim "I can't see a better plan," but a checkable certificate of nonnegative reduced cost. I've also confirmed along the way that "too many extreme points" isn't a fatal problem — the whole process never enumerated any extreme points; at each step, a single optimization problem constructs exactly the column that most deserves to be added under the current prices.

Let me draw a clear line between this mechanism and neighboring methods. It isn't just an ordinary case of solving several submodels in parallel and stitching them together: the master is an exact convex-combination LP, pricing is reduced-cost separation for the full LP, and the two close the loop into a dual certificate. Nor is it Benders: Benders fixes the master variables and lets the subproblem generate violated cuts that progressively tighten the master's feasible region — that's row generation. Here, instead, the extreme points of the subproblem's feasible region become columns that progressively expand the master's variable space — that's column generation. Precisely because "a column is a complete, locally feasible plan," this fits especially well with the cutting patterns of cutting stock, the duties of crew scheduling, and the routes of vehicle routing — a column is a pattern, a duty, a route.

Last, the boundary conditions — I won't claim these as verified, only state the scope of applicability clearly. If `X_k` is unbounded, the convex-combination representation needs to be supplemented with extreme rays, and the corresponding columns are improving directions rather than convexity-normalized plans; the small bounded example above doesn't cover this case, and I'd want to verify it separately on a block that has rays. If the original problem has integer structure, this LP machinery gives a relaxation, usually a strong lower bound, but integer optimality generally still requires branch-and-price. None of these extensions change the core that I've verified: fold local structure into columns, hand global coordination to the master, and hand the discovery of columns to a pricing problem driven by dual prices.
