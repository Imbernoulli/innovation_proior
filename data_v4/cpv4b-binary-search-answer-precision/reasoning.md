With `n, m <= 10^5` the product table has up to `n*m = 10^10` entries, so materializing and sorting it is out before I start. And with `a[i], b[j] <= 4*10^9` a single cost `a[i]*b[j]` reaches `4*10^9 * 4*10^9 = 1.6*10^19`. That second number is the one that decides this problem: it sits above the signed 64-bit ceiling (`~9.22*10^18`), above the upper bound of any answer-value search I would run (`1.6*10^19` itself), and even unsigned 64-bit only reaches `~1.84*10^19`, so there is barely a whisker of headroom. The answer I must print can itself *be* that maximal product, so overflow is on the main path, not a corner I patch later. I carry the candidate answer and every product in `__int128`, and I make that decision first.

So I need an implicit K-th selection. A heap that pops the smallest-unseen frontier `K` times dies on contact: `K` can be `n*m = 10^10`. What survives is binary search on the answer value. All weights are positive, so `f(x) = #{(i,j) : a[i]*b[j] <= x}` is nondecreasing in `x`, and the `K`-th smallest cost is the smallest `x` with `f(x) >= K`. That `x` is necessarily an attained product: just below it `f < K`, so the count can only cross `K` by passing a real cost, which means the value I converge to equals that cost — the search target is well defined and lands on an actual pairing. Bisecting `x` over `[1, 1.6*10^19]` with a count that costs `O(n log m)` gives `O(n log m * log(MAXPROD))`; at `n = m = 10^5` that is `n * log2 m ~ 1.7*10^6` comparisons per outer step across ~64 steps, about `1.1*10^8` `__int128` comparisons, and a run at that size finishes in roughly 0.58 s using under 5 MB — inside the 2 s / 256 MB budget.

For `f(x)` I sum over bases the count `#{j : a[i]*b[j] <= x}`. Sort `b` once ascending; since `a[i] > 0`, the product `a[i]*b[j]` increases in `j`, so the qualifying catalysts form a prefix and I binary-search its length.

The tempting way to find that prefix is to divide: count `b[j] <= x / a[i]`. For positive integers `a[i]*b[j] <= x` iff `b[j] <= floor(x / a[i])`, so *integer* floor division would in fact be correct — but `x` runs to `1.6*10^19` and does not fit the integer type, and the reflex fix for that, `(double)x / a[i]`, is poison at this scale. A `double` carries ~53 mantissa bits, so `9000000000000000001` is not representable and rounds to `9000000000000000000.0`; then a comparison like `9e18 <= (double)(9e18 + 1) / 1` returns false and `f` undercounts by one at exactly the magnitudes the hidden tests aim at — the binary search would converge one product off with no crash to warn me. So I never form a `double` from these values. Instead I keep the test as an exact product: for each base I binary-search the first `j` where `(i128)a[i] * b[j]` exceeds `x`, and add that index. No division, no float — every comparison is an exact 128-bit product against an exact 128-bit threshold.

Let me trace the division-as-count idea on a tiny adversarial instance, ignoring the overflow for a moment to isolate the rounding question. Take `a = [3]`, `b = [2]`, so the single product is `6`. Ask `f(7)`: the true condition is `3*2 = 6 <= 7`, true, so `f(7)` should be `1`. Division version: `q = 7 / 3 = 2` (floor), then `#{b[j] <= 2} = #{2 <= 2} = 1`. Matches — `1`. Now `f(5)`: true condition `6 <= 5` is false, so should be `0`. Division: `q = 5/3 = 1`, `#{b[j] <= 1} = 0`. Matches. So far floor division happens to agree.

**The first bug — division agrees on integers but I almost shipped it in `double`.** The agreement above is real *for integer floor division*, because `a[i]*b[j] <= x` iff `b[j] <= floor(x / a[i])` when everything is a positive integer (this is the standard "`b <= floor(x/a)` iff `a*b <= x`" identity). So integer floor division would actually be correct here — but only if `x` fits in the integer type, which it does **not**: `x` reaches `1.6*10^19`. The trap I have to avoid is the version people reach for when they notice the overflow and "fix" it by switching the division to floating point: `double q = (double)x / a[i];`. Let me trace why that is poison on an adversarial case. Take `a[i] = 1` and `x = 9000000000000000001` (just above `9*10^18`), with a `b` value exactly `9000000000000000000`. True: `1 * 9e18 = 9e18 <= 9e18 + 1`, so this `b[j]` qualifies. Floating: `(double)9000000000000000001` cannot be represented exactly — `double` has 53 bits of mantissa, about 15-16 significant decimal digits, so `9000000000000000001` rounds to `9000000000000000000.0` (or even down to `8999999999999998976` depending on the value). Dividing by `1` gives that rounded value, and comparing `9000000000000000000 <= 8999999999999998976` returns **false** — I would undercount, the binary search would converge to the wrong `x`, and the final answer would be off by a full product. The episode's lesson is sharp: any path through `double` silently corrupts comparisons at these magnitudes. So I discard division-in-floating-point entirely.

No division, no floating point: every comparison is an exact `__int128` product against an exact `__int128` threshold. Re-trace `f(15e9)` on the sample with this code. `ai = 4`: products `4*2=8, 4*5=20, 4*3e9=12e9`, all `<= 15e9` -> `lo` walks to 3. `ai = 2`: `4, 10, 6e9` all `<= 15e9` -> 3. `ai = 3e9`: `3e9*2 = 6e9 <= 15e9` yes, `3e9*5 = 15e9 <= 15e9` yes, `3e9*3e9 = 9e18 <= 15e9` no -> stops at `lo = 2`. Suppose I had instead written the seductive `i128 hi = 4000000000ULL * 4000000000ULL;`. Trace the right-hand side: `4000000000ULL * 4000000000ULL` is computed in `unsigned long long` *before* the assignment widens it. The true value `1.6*10^19` is below the `u64` max `1.844*10^19`, so it actually fits this time — `hi` would be `16000000000000000000`. That looks safe, which is exactly why it is dangerous: it lulls me into the pattern. If I ever bumped the bound to `5e9*5e9 = 2.5*10^19`, the `u64` multiply would wrap to `2.5e19 - 1.844e19 = 6.55e18` and the search range would silently collapse below the true answer, and the binary search would return garbage with no crash. To make the code robust to that whole class of mistake I force each factor to `i128` first, so the multiply happens in 128-bit and can never wrap. I also confirm `mid = lo + (hi - lo)/2` rather than `(lo + hi)/2`: with `lo, hi` near `1.6*10^19`, `lo + hi` is about `3.2*10^19`, which exceeds `u64` but is comfortably inside `i128` (`~1.7*10^38`), so either form is safe here — but `lo + (hi - lo)/2` is the form that stays safe even if the bound grows, so I keep it.

The outer loop is a plain `lo = 1`, `hi = 1.6e19` bisection that pulls `hi` down to the smallest tested `x` with `f(x) >= K`. I write the midpoint as `lo + (hi - lo)/2` so it cannot overflow even if the range widens. `K` itself reaches `10^10`, so it lives in a `long long` and I compare the count against `(i128)K`.

The extremes then fall out. `K = 1` returns the minimum product and `K = n*m` the maximum — the maximum being the most overflow-prone value in the problem.
